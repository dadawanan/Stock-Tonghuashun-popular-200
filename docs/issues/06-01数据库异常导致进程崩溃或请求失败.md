# 📝 技术缺陷分析与性能优化总结报告

## 1. 缺陷现象 (Problem)

在线上监控与 PM2 日志中发现，系统的两个核心服务 `stock-api`（业务接口服务）和 `stock-scheduler`（定时任务服务）频繁抛出相同的数据库异常导致进程崩溃或请求失败。

**核心错误日志截取：**

```text
sqlalchemy.exc.IntegrityError: (raised as a result of Query-invoked autoflush; consider using a session.no_autoflush block if this flush is occurring prematurely)
(sqlalchemy.dialects.postgresql.asyncpg.IntegrityError) <class 'asyncpg.exceptions.UniqueViolationError'>: duplicate key value violates unique constraint "stock_master_pkey"
DETAIL:  Key (stock_code)=(605277.SH) already exists.

```

---

## 2. 原因分析 (Root Cause)

经过代码走查与执行流追踪，导致该问题的根本原因有以下三点：

### ① 传统的“先查后改”逻辑在高并发下失效

原代码在更新股票主表（`stock_master`）时，采用的是经典的 **For 循环 + 逐条查询** 逻辑：

1. 拿着 `stock_code` 去数据库 `GET` 查一下是否存在。
2. 如果存在就更新（Update），不存在就插入（Insert）。

当 `stock-scheduler` 在后台同步大批量股票数据的同时，用户在前端触发了 `POST /api/run-all` 接口，两个进程同时对同一只股票（如 `605277.SH`）进行“先查后改”。由于时间差，两者可能同时判定该股票“不存在”，随后同时发起 `INSERT`，导致后提交的进程触发**主键唯一性约束冲突**。

### ② SQLAlchemy 的 Autoflush 机制引发提早崩溃

在原代码的循环中，当第一条新股票被 `session.add()` 放入内存后，循环进入第二条股票并执行 `await session.get()`。
此时，SQLAlchemy 为了保证查询的准确性，会默认触发 **Autoflush（自动刷新）**，强行将内存中第一条还未 commit 的 `INSERT` 语句推向数据库。在推向数据库的瞬间，直接触发了唯一性约束崩溃，导致**后续的查询和处理逻辑甚至还没开始就死掉了**。

### ③ 输入源数据存在重复项隐患

若上游上报的股票数据列表（`rows`）自身由于清洗问题包含了重复的 `stock_code`，在没有事务提交隔开的情况下，连续的 `session.add()` 会在最终 Commit 时引发自我主键碰撞。

---

## 3. 解决思路 (Design Thoughts)

为了彻底根除主键冲突，并大幅提升海量股票数据的同步性能，我们放弃了“在 Python 内存层做判断”的传统做法，改用“将并发与去重逻辑下沉到数据库层”的架构思路：

1. **内存防卫（防御性编程）**：在数据进入数据库前，首先在 Python 内存中对入参列表进行快照去重，确保单次批处理内部无冲突。
2. **原子化 Upsert（存在即更新）**：利用 PostgreSQL 核心特性 `ON CONFLICT (stock_code) DO UPDATE`。让“检查是否存在”、“插入”、“更新”这三个动作为一条 SQL 语句，在数据库内部原子化完成，彻底从物理层消灭并发锁竞争。
3. **I/O 批量化（Batching）**：将原本成百上千次的传统 `for` 循环单条数据库 I/O 交互，压缩为**1次批量查询 + 1次批量 Upsert**，将数据库吞吐量提升数个量级。

---

## 4. 最终解决方案 (Implementation)

我们在 `/src/stock_service/crud/v2_crud.py` 中重构了 `upsert_stocks` 函数，实现了无懈可击的批量安全写入。

### 📊 优化前后对比总结

| 指标 | 优化前 (Before) | 优化后 (After) |
| --- | --- | --- |
| **数据库 I/O 次数** | $2 \times N$ 次（$N$ 为股票数量） | **固定仅需 2 次** |
| **并发安全性** | 极差（多进程同时运行必定碰撞崩溃） | **绝对安全**（由 PG 锁机制保障原子性） |
| **内存重复数据抗性** | 无法防御（直接引发 Commit 异常） | **完美防御**（通过 `seen_codes` 提前过滤） |
| **业务指标统计** | 容易受到中断影响 | 稳定通过 `existing_set` 准确计算纯新增数 |

### 💻 核心重构代码

```python
from sqlalchemy import select, func
from sqlalchemy.dialects.postgresql import insert as pg_insert
from sqlalchemy.ext.asyncio import AsyncSession

async def upsert_stocks(session: AsyncSession, rows: list[dict]) -> int:
    """
    使用 PostgreSQL ON CONFLICT DO UPDATE 批量 upsert stock_master，返回新增行数。
    """
    if not rows:
        return 0

    # 1. 内存去重：防止 rows 内部自带重复的 stock_code 导致 Postgres 报错
    seen_codes: set[str] = set()
    unique_rows: list[dict] = []
    for r in rows:
        code = r.get("stock_code")
        if code and code not in seen_codes:
            seen_codes.add(code)
            unique_rows.append(r)

    # 2. 预计算衍生字段 + 清洗字段，一次性构建所有 values
    value_rows: list[dict] = []
    all_codes: list[str] = []

    for r in unique_rows:
        stock_code = r["stock_code"]
        all_codes.append(stock_code)

        derived = _derive_stock_fields(stock_code, str(r.get("stock_name", "")))
        model_fields = {k: v for k, v in r.items() if k in _STOCK_MASTER_FIELDS}
        model_fields["market"] = derived["market"]
        model_fields["code_digits"] = derived["code_digits"]
        model_fields["is_st"] = derived["is_st"]
        model_fields["market_code"] = str(model_fields["market_code"]) if model_fields.get("market_code") is not None else None
        model_fields.setdefault("status", "active")
        value_rows.append(model_fields)

    # 3. 先批量查询已存在的 stock_code，用于后续统计新增数量
    existing_result = await session.execute(
        select(StockMaster.stock_code).where(StockMaster.stock_code.in_(all_codes))
    )
    existing_set = {row[0] for row in existing_result.all()}

    # 4. 构建并执行高效率的批量 Upsert 语句
    stmt = pg_insert(StockMaster).values(value_rows)
    stmt = stmt.on_conflict_do_update(
        index_elements=["stock_code"],
        set_={
            "stock_name": stmt.excluded.stock_name,
            "market": stmt.excluded.market,
            "market_code": stmt.excluded.market_code,
            "code_digits": stmt.excluded.code_digits,
            "is_st": stmt.excluded.is_st,
            "updated_at": func.now(), # 由数据库生成最新更新时间
        },
    )
    await session.execute(stmt)

    # 5. 计算真正新增的行数返回给上游
    return sum(1 for c in all_codes if c not in existing_set)

```

## 5. 最终结论

该方案上线并重启 PM2 服务（`stock-api` / `stock-scheduler`）后，通过对日志的持续追踪，**主键冲突报错彻底消失**。大批量数据同步时的系统 CPU 与数据库负载显著下降，接口响应速度得到大幅提升。
